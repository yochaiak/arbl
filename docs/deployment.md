# Hetzner deployment

The repository now contains a deployable foundation and runtime manifests. **A rendered chart is not a live deployment or a capacity result.** The release ledger records live cloud validation separately. No cloud resources are created by the local validation commands below.

## What is provisioned

Terraform owns eight fixed Ubuntu amd64 servers: three K3s control-plane servers with embedded etcd, three data nodes, and two application nodes. Each role uses a spread placement group. A private network has separate fixed, standard-worker, and vendor-worker subnets. An ingress load balancer forwards TLS to application-node NodePorts using PROXY protocol. Traefik trusts PROXY headers only from the load balancer private IP, preserving client IP for AdScore verification. If the subnet changes, update `deployment/operators/traefik.yaml` accordingly. Administration is limited to explicit CIDRs; no public database service is created. K3s encrypts Kubernetes Secrets and uses WireGuard between nodes. Browser workers install the vendored Chromium user-namespace seccomp profile; browser pods remain non-root with all container capabilities dropped. The profile allows `chroot` inside Chromium’s user namespace so the browser sandbox can stay enabled.

Cluster Autoscaler owns elastic servers; Terraform does not own their lifecycles. The configured standard and vendor pool ceilings sum to at most 80 nodes, with two warm standard nodes and no mandatory vendor nodes. Eight fixed servers, the load balancer and eighty workers consume 89 of the network's 100 attachment slots. [Hetzner network limits](https://docs.hetzner.com/networking/networks/overview/)

KEDA reads **admitted**, queued `browser_sessions` from PostgreSQL. Each Job claims one session. Database admission remains the authoritative aggregate 500-session ceiling across pools, projects, targets, licenses and proxies. Kubernetes retries are disabled; ABRL owns logical attempt recovery. Jobs and runtime pods cannot be removed by ordinary autoscaler scale-down while active. KEDA uses accurate scaling and gradual rollout. [PostgreSQL scaler](https://keda.sh/docs/2.21/scalers/postgresql/), [ScaledJob lifecycle](https://keda.sh/docs/2.21/reference/scaledjob-spec/)

Cloud Chromium uses a lightweight runner plus separate authenticated browser and broker pods. `CloudRuntime` scopes ingress to the owning Job and session, injects only the selected provider secret references into the broker, and confirms runtime pod UIDs are gone before reporting cleanup. Browsers cannot access DNS, PostgreSQL, metadata services or direct Internet. Brokers resolve permitted targets and own provider connections. The chart defaults cloud workers off pending the live egress acceptance test. Cloud profile transfer is encrypted and still requires cross-worker live restoration evidence. CloakBrowser and Kameleo have separate image recipes and selected-secret wiring. The Kameleo engine runs as an amd64 sidecar under UID1001 with shared export volume and at least 2 GiB shared memory. The engine image must be digest-pinned and licensing origins explicitly configured. Those adapters remain unverified until licensed integration checks pass; the presence of a vendor node pool does not establish adapter readiness. Manual Chrome has a dedicated amd64 image with signed-package Google Chrome and Xvfb, configured through `cloudWorkers.manualImage`. It uses the standard worker pool and the authenticated operator viewer; only a person's recorded controls count as human activity. Its live cloud handoff/isolation validation remains a deployment acceptance gate.

Build `infrastructure/docker/cloakbrowser.Dockerfile` with a BuildKit `cloak_license` secret to preinstall its licensed binary; never pass the key as a build argument. Build `infrastructure/docker/kameleo.Dockerfile` for the SDK process and resolve the official `kameleo/kameleo-app` image to a digest for the engine sidecar. Both accept the tested browser base via `ABRL_BROWSER_BASE`. Configure `cloudWorkers.cloakImage/kameleoImage/kameleoEngineImage`, provider credentials in `abrl-browser-vendors`, and exact documented Kameleo control origins before enabling the vendor ScaledJob. Kameleo SDK/engine major-minor compatibility is checked at launch. [Kameleo Docker](https://developer.kameleo.io/integrations/docker/), [CloakBrowser install](https://github.com/CloakHQ/CloakBrowser)

Initial browser reservations are **hypotheses**, not benchmarks: standard 2 vCPU/4 GiB and vendor 4 vCPU/8 GiB plus 0.35 vCPU/640 MiB runner/broker overhead per session. The Kameleo SDK sidecar adds another 0.1 vCPU/128 MiB. The example uses configurable ccx63 nodes and 30/50 standard/vendor maxima; preflight checks actual architecture, memory, CPUs and location availability. At 500 vendor sessions the browsers alone request 2,000 vCPU and 4,000 GiB. Unknown prices remain null; there is no monetary cap. `cloud-preflight.py --estimate-only` displays fit and resource estimates. Smaller instances are acceptable only if the measured slot count and configured node ceiling support the desired load.

For live cost visibility, supply `ABRL_FLEET_PRICES_JSON` with `currency`, `node_hourly.standard`, `node_hourly.vendor` and optional `fixed_hourly`. Values are configured hourly prices; use null for unknowns. The fleet API deduplicates actual node names reported by live runner heartbeats. Its estimate covers observed runner nodes, while idle nodes and nodes hosting only browser/broker pods may remain unobserved. It reports missing prices and a known subtotal separately; it does not label this partial inventory as the whole fleet bill.

Proxy inventory accepts an optional `cost_per_gb` and explicit ISO currency `cost_currency`. Each completed attempt records its measured transport counters and the rate used, so connection recovery retains prior attempt usage. Research multiplies measured proxy payload bytes by the configured rate using decimal GB (1,000,000,000 bytes). Direct vendor licensing/control traffic is excluded from proxy usage cost. Transport overhead, subscriptions, discounts, tax and provider invoice adjustments are not measured; this component is labeled an estimate. Infrastructure and browser-license costs remain unknown unless supplied, so a known proxy estimate never becomes a complete workflow cost. An explicit existing all-in `cost_per_session` input remains a separate configured estimate. Historical snapshots remain immutable and show metering unavailable when it was not recorded.

## Prerequisites

Use a dedicated Hetzner project, existing SSH key IDs, real domain/DNS and TLS certificate, OIDC client, private container registry images, object-storage access keys, and externally retained encryption/recovery keys. Provider server quotas are not exposed by the public account API: provide recent console/support evidence in a file containing `verified_at`, `source`, and `server_limit`. Preflight compares this with the live server inventory. Licensed adapters additionally require Linux amd64-compatible entitlements and tested versions. AdScore requires its own compatible test zone.

Required local tools: Terraform >=1.10, Helm 3, kubectl matching Kubernetes minor, Python/uv, SSH and Docker for building images. Pinned operator/K3s versions are in `deployment/operators/versions.json`; the autoscaler minor matches Kubernetes. Do not use mutable `latest` image tags in a release. Resolve application tags to registry digests in the final deployment values.

## State, secrets and bootstrap

1. Create a dedicated **never-versioned** state bucket. Export `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_SSE_CUSTOMER_KEY` (base64 32 bytes) outside the repository. Fill a copy of `backend.hcl.example`. Terraform's SSE-C key must be supplied by environment, not backend config. Keep encrypted state-history copies in a separate versioned DR bucket. Hetzner does not support conditional PUT/DELETE on versioned buckets. [Terraform S3 backend](https://developer.hashicorp.com/terraform/language/backend/s3), [Hetzner compatibility](https://docs.hetzner.com/storage/object-storage/supported-actions/)
2. Export `ABRL_STATE_ENDPOINT` and `ABRL_STATE_BUCKET`, then run `uv run python scripts/cloud-preflight.py --config <filled-cloud.json> --check-state --output <state-evidence.json>`. This writes and removes a temporary encrypted object; a competing conditional creation must fail with 412 and a read without its customer key must fail. Do not proceed on a failed check.
3. Export `HCLOUD_TOKEN`, fill `terraform.tfvars`, then run `terraform init -backend-config=<backend-file>`, `terraform plan -out=<plan-file>` and review the fixed resources before `terraform apply <plan-file>`. This step incurs charges. The repository task does not run it automatically.
4. Save `terraform -chdir=infrastructure/terraform output -json > <inventory.json>`. Generate an external recovery-managed 32+ character join-token file, mode 0600. Verify SSH host keys through trusted provider metadata; bootstrap requires `StrictHostKeyChecking=yes`. Run `python3 scripts/cloud-bootstrap.py --inventory <inventory.json> --join-token-file <private-token>`. It checks the pinned installer digest and streams configuration over SSH; tokens are absent from Terraform state.
5. Retrieve `/etc/rancher/k3s/k3s.yaml` through verified SSH, change its loopback server to an allowed control-node address and keep mode 0600. Test `kubectl get nodes`. Retain the K3s server token and encryption configuration externally; an etcd snapshot without these does not constitute a recovery backup.
6. Create namespace `abrl`. Fill a private copy of `deployment/runtime.env.example`, mode 0600. Use `python3 scripts/cloud-secrets.py --env-file <private-file>` to install secrets through stdin. The chart receives secret names, not secret values. Place Oxylabs references in a separate mode-0600 file (`PROXY_USER=<credential>`, `PROXY_PASSWORD=<credential>`) passed with `--proxy-env-file`. It creates `abrl-proxy-providers` with uppercase reference keys; the broker receives them as `ABRL_SECRET_<REFERENCE>` only; neither browser nor broker receives `abrl-runtime`.
7. Run `scripts/cloud-install-operators.sh`. It installs pinned Hetzner CCM/CSI, CloudNativePG, Barman Cloud, KEDA and Traefik charts. Configure a TLS Secret named `abrl-tls` (or the selected chart value) and point DNS to the Terraform ingress IP. Do not expose the unconfigured domain publicly.
8. After K3s secret encryption is confirmed, install the autoscaler configuration using `cloud-bootstrap.py --autoscaler-secret --inventory ... --join-token-file ... --firewall-id <id>`. This writes worker join configuration to a Kubernetes Secret. The autoscaler uses its own provider token. It uses the three control-node addresses when bootstrapping a new worker.

The bootstrap does not disable certificate verification for application connections. Its initial agent endpoint reachability probe uses `/ping`; the actual K3s join authenticates with the join token. A control-node failure is tolerated by K3s after formation. Confirm bootstrap and replacement behavior during the node-loss rehearsal.

## Build and deploy the application

```sh
docker build --platform linux/amd64 -f infrastructure/docker/api.Dockerfile --target base -t <registry>/abrl:<revision> .
docker build --platform linux/amd64 -f infrastructure/docker/api.Dockerfile --target browser -t <registry>/abrl-browser:<revision> .
docker build --platform linux/amd64 -f infrastructure/docker/api.Dockerfile --target manual -t <registry>/abrl-manual:<revision> .
docker build --platform linux/amd64 -f infrastructure/docker/web.Dockerfile --build-arg NEXT_PUBLIC_API_URL=https://<domain> -t <registry>/abrl-web:<revision> .
```

For instrumented research, build `infrastructure/docker/verifier.Dockerfile`, configure `verifier.enabled/image` and the optional AdScore secret fields. The Node verifier runs as an API sidecar bound only to loopback; its response key is excluded from the API runtime Secret. Only a complete real signature smoke test can mark it ready.

Build all cloud images for `linux/amd64`, including API and web when building from an Apple Silicon Mac. Push reviewed images to the configured registry. Set `image.repository/digest`, `webImage.repository/digest`, `cloudWorkers.browserImage` (a complete digest reference), domain, storage endpoints and autoscaler network ID in a private chart values file. Digest values override tags; actual runtime pod UIDs, nodes and container image IDs are recorded with the execution. Use `scripts/cloud-deploy.sh <values.yaml>`: it creates the database foundation first, waits for CNPG Ready, runs the additive migration as a pre-upgrade hook, then starts/updates application replicas. Do not bypass this order on a new cluster. CNPG creates the dedicated `abrl_scaler` login from its separate password Secret; the migration wrapper waits for reconciliation and grants only schema USAGE and SELECT on `browser_sessions`. Set `ABRL_SCALER_PASSWORD` to the same password encoded in the scaler's ordinary PostgreSQL DSN, which is distinct from the application's SQLAlchemy DSN.

`ABRL_DEPLOYMENT=cloud` is mandatory. Local bootstrap bearer authentication must stay disabled in cloud. OIDC authenticates users; `ABRL_METRICS_TOKEN` authenticates Prometheus independently. API trusted forwarded addresses are limited to pod CIDR `10.42.0.0/16`; ingress NetworkPolicy further restricts clients. If you change pod/service CIDRs, update those policies and Uvicorn's trusted proxy setting together. Set `controlPlaneCidrs` to the private API server addresses from Terraform; the policies allow both the Service IP and its endpoint IPs so service DNAT does not block controller/database access.

Set `ABRL_CONTROLLED_ORIGIN` and `ABRL_WEB_ORIGIN` to the same HTTPS origin as the chart's DNS/TLS host. Before deployment, run `cloud-preflight.py --config <filled-cloud.json> --require-runtime` with the runtime environment loaded securely. This rejects example domains, a different fixture hostname, non-HTTPS URLs, custom ports and path/query credentials. It checks configuration consistency; actual DNS resolution and certificate validity still require the live deployment check.

## Data and backups

CloudNativePG runs three instances with synchronous `ANY 1`, required durability, supervised primary update and per-host anti-affinity. Redis uses three persistent instances and three Sentinels; PostgreSQL/outbox remains authoritative during Redis failure. ClickHouse has three replicas backed by a three-member Keeper quorum, with a replicated replacing event table. [CNPG synchronous replication](https://cloudnative-pg.io/docs/1.28/replication/)

Enable `postgres.backupsEnabled`, `backupEndpoint` and `backupDestination`. The pinned Barman Cloud v0.16 plugin supports Hetzner **SSE-C** through `s3Credentials.sseCustomerKey`; the manifest always supplies that secret for base backups, WAL archiving and recovery. Never reuse a backup path with a changed encryption key. This removes the need for an unsigned encryption “attestation.” [Official Barman SSE-C support](https://cloudnative-pg.io/plugin-barman-cloud/docs/object_stores/#server-side-encryption-with-customer-keys-sse-c)

`cloud-backup.py mirror --native-sse` replicates native Barman objects to a versioned bucket in another location using download/upload and explicit source/destination SSE-C. It retains Barman paths, propagates no deletions and verifies each new copy by reading it back and comparing SHA-256. For already application-encrypted profiles/artifacts, ordinary `mirror` adds authenticated chunk encryption, including encrypted name manifests and a final authenticated frame that detects truncation. It can recover a manifest after a process stops between object and manifest upload. Full mirrors run every five minutes; an independent WAL-only mirror runs every minute so copying a large base backup cannot delay WAL dispatch. Each job prevents overlap with its own previous occurrence. Supply credentials using `abrl-backup-mirror`, never Helm values.

The profile Fernet key, backup chunk-encryption key, Barman SSE-C keys, Terraform SSE-C key and K3s recovery material are separate keys with external recovery copies. Server snapshots do not back up attached volumes. [Hetzner backup scope](https://docs.hetzner.com/cloud/servers/backups-snapshots/overview/)

## Live acceptance and remaining evidence

Run `cloud-verify.py --output <evidence.json>` for cluster health. It does not claim failover, isolation or capacity merely because pods are ready. `cloud-load.py --url https://<domain> --template <owned-fixture-batch.json> --maximum 500 --acknowledge-owned-fixture --output <new-evidence.json>` runs real 100, 250 and 500 stages, stops/cancels on failure and records per-session results, peak active browsers and API responsiveness. Use an OIDC cookie in `ABRL_LOAD_COOKIE`; never put it in arguments. The fixture must remain active long enough to observe the claimed concurrency. Project/target limits must explicitly permit each stage. Do not relax proxy/license caps to obtain a pass.

Live gates still include: external connection denial despite explicit IPs, redirects/resource/WebSocket behavior, cross-session broker and CDP isolation, standard browser sandbox support, replica failure, node loss, partition/fencing, encrypted backup readback, PITR to a new cluster and 100→250→500 load. Capture CPU, memory, startup, queue delay, profile persistence and proxy metrics alongside the load JSON. Missing licensed or vendor access leaves that vendor unverified. A successful simulated run cannot satisfy any of these gates.
